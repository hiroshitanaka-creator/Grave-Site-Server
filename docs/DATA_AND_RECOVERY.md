# データ契約・移行・復旧

## 保存対象と識別

日記解析の `entry` は日記原文、APIの `message` は配信用本文です。日記原文を要約で置き換えたり、
日記を自動的に配信へ回したりしません。関連を残す場合は `memory_refs` に出典IDを指定します。
参照先の検証・取得・生成は未実装です。旧日記CLIのスナップショットと新規メッセージ台帳は併存します。

| 項目 | 保存・検証 |
|---|---|
| recipient / message | 空白だけは拒否。本文・前後空白をそのまま保持。上限200 / 1000文字 |
| date | YYYY-MM-DD。Calendar終日イベントの日付。翌日を表せない9999-12-31は拒否 |
| tags / memory_refs | 文字列配列を順序も含めて保持。各100件、要素200文字まで |
| source | 入力元を保持。既定gpts-actions、上限100文字 |
| request_id | 依頼のキー。上限200文字。台帳全体で一意。API_KEY別のテナント分離はない |
| calendar_id | 明示値、または登録時のGOOGLE_CALENDAR_IDを固定保存。未設定からの初回設定はPUT可能。設定済み宛先の移動は別途移行 |
| publish_at | タイムゾーン必須の日時。UTCへ正規化。未指定なら即時登録 |
| revision | 新規1、訂正で増加。過去版はrevisionsへ保存 |

余分な入力項目は422で拒否します。文字数はPythonのUnicode文字数で、バイト数や表示幅ではありません。
`tags` / `memory_refs` の順序も内容の一部です。既定値を補った正規化後の内容をSHA-256で照合します。
登録時に省略したcalendar_idの環境既定値が変わると、同じ要求でも競合になり得ます。
再送では最初と同じ設定を使うか、保存したrecord_idのGET / retryを利用してください。

`request_id` があればそのハッシュから `msg-...` IDを決定し、なければUUIDを発行します。
同じキーと同じ初回内容は既存記録を返して未完了処理だけを試みます。訂正後の初回依頼の再送も、
初回のrequest_hashと照合して現在版を返し、訂正を巻き戻しません。内容違いは409です。
訂正PUTはexpected_revisionを照合し、処理中なら409、同じ内容なら版を増やしません。
request_idの有効期限・自動削除はなく、台帳を失うと冪等性の履歴も失われます。

## 永続台帳を追加した理由

Driveの同名検索は一意制約や排他トランザクションではありません。そのまま依頼IDの重複排除を置くと、
並行実行の競合を防げないため、保存状態の正本を小さな台帳へ分離しました。

- **単一ホスト:** 標準ライブラリのSQLite。ローカルの永続ディスクで利用し、NFSやCloud Storageマウントに置かない。
  BEGIN IMMEDIATEで更新を直列化し、記録と版の保存を同一トランザクションで行う。
- **複数インスタンス:** 任意導入のFirestore。record単位のトランザクションを使用する。
  新規DBの作成や料金・IAMの変更は実施していない。クラウド利用前の検証ゲートはVALIDATION.mdを参照。
- **Cloud Run:** 一時ディスク上のSQLite設定は明示的に拒否する。Firestore以外の共有ストアへ変更する場合は、
  MessageStoreのトランザクション契約を満たすアダプタと同じ障害テストが必要。

FirestoreのbodyはJSON文字列です。現実装のジョブは全記録を読み込み、古い更新時刻から処理します。
`--limit` は外部処理件数の上限であり、Firestore読取件数の上限ではありません。
大量データでは索引・ページ分割・読取コストを評価してから利用します。

## 配信と障害時の意味

台帳保存後、DriveとCalendarを独立に試行します。片方の失敗がもう片方の結果を隠しません。
配信前に台帳をunknownへ更新し、外部処理完了後に成功を記録します。外部成功直後にプロセスが停止した場合や、
成功状態の保存に失敗した場合はunknownが残り、固定IDで実結果を照合します。

- Drive: generateIdsで事前発行したIDを台帳へ保存してからJSONを作る。
  `message_<record_id>_v<revision>.json` を版ごとに追加し、同じ日付の別記録も旧日記も上書きしない。
  appPropertiesに記録ID・版・ハッシュを持つ。既存IDの照合と409後のGETで再送を扱う。
- Calendar: `grave` + record_idのSHA-256をイベントIDとする。本文訂正でもIDは同じ。
  記録ID・版・ハッシュをprivate extendedPropertiesに保持し、更新にはETagのIf-Matchを付ける。
  既存イベントがより新しい版なら古いワーカーは更新しない。409 / 412では再読込する。
- 1記録に300秒の期限付きリースを設定する。状態更新にはトークンと期限を照合する。
  強制終了時は期限後に同じIDで再試行する。訂正前には残ったリースをretryで解消する。
- 同版のCalendar本文が手で編集されていればconflictを返す。手動変更を黙って戻さない。
  ただし新しい版への訂正は配信先の内容を書き換える操作である。
- Driveの照合はID・フォルダ・メタデータで行う。第三者が内容だけ改変しappPropertiesを残すケースは検出しない。
  保存フォルダの書込み権限を限定し、復旧時はJSON内容・ハッシュも確認する。

外部APIを含むexactly-onceを保証しません。長時間停止した旧ワーカー、外部の手動変更、権限喪失、
台帳を過去へ戻した場合などは照合が必要です。本文・時刻による曖昧な一致でイベントを採用しません。
`unknown` のまま再読込自体に失敗した場合もunknownを維持します。連携を無効にしても既存の失敗・不明状態は消しません。

## 復旧手順

1. GET /messages/{record_id} で台帳と両連携の状態・IDを確認する。API要求自体が500だった場合、
   登録済みか不明なので同じrequest_idで再送する。新しいキーを発行しない。
2. failedの認証・フォルダ・Calendar ID・権限・制限を修正する。プロバイダの生エラーは返さず安全なエラーコードを保存する。
3. POST /messages/{record_id}/retry またはgrave-deliverを実行する。既にsaved / publishedの段階は呼び直さない。
4. unknownなら固定IDを直接Googleで照合する。GETが404でも権限喪失の可能性があるため、まず同じ認証主体と権限を確認する。
5. conflict / stale_worker / external_editが残る場合、現在版とGoogle側の版・本文を確認する。
   新規依頼として再登録する前に、既存イベントの扱いを運用責任者が決める。
6. 300秒を過ぎたリースは再試行で取得可能。稼働中のワーカーを停止せず台帳を手編集しない。

`grave-deliver` は1回の有限処理です。failed / unknown / busyがあれば終了1、なければ0です。
恒久的失敗も自動選別で除外せず次の起動で再試行します。件数・失敗/不明・待機最古時刻・
ジョブ実行間隔を監視し、認証エラーを無制限に放置しないでください。
レコードID・版・段階・状態をログ出力し、本文はジョブログに出力しません。

## バックアップと戻し方

SQLiteは本体を単純コピーせずSQLite backup APIを使用します。宛先は既存ファイルを上書きしません。
秘密情報を含まなくても本文・宛先は含むため、保存先のアクセスとバックアップの暗号化・保管期限を決めます。

```bash
mkdir -p backups
.venv/bin/python -m src.messages.backup --source data/messages.sqlite3 --destination backups/messages-before-change.sqlite3
```

復元時はServiceとジョブを止め、現DBも別名へバックアップし、復元コピーを別パスに置きます。
`MESSAGE_DB_PATH` を復元コピーへ向け、外部フラグfalseで内容・版・IDを読み取り確認します。
その後テスト対象で外部照合し、未完了処理を再試行します。**古いバックアップから戻すと、
その後発行されたDrive IDや依頼自体が失われる**ため、Google側と差分照合するまで本番送信を再開しません。
メッセージ本文だけのDrive JSONは、台帳のリース・全配信状態・初回request_hashを含む完全バックアップではありません。

Firestoreは対象DBのマネージドエクスポート/バックアップを使い、親collectionだけでなくrevisionsも保護します。
復元先は隔離DBにし、件数・版・固定IDとGoogle側を照合します。費用・復元権限・保管先を事前確認します。
Firestoreバックアップ/復元とそのIAMは本作業では実行していません。

コードを旧版へ戻す場合も新台帳を消さず保管します。旧版APIは新台帳を理解しないため、
外部連携を停止した状態で切り戻します。旧版APIで日付ファイルに再保存すると、旧来の上書き問題が再発します。

## 0.1.0からの非破壊的移行

実データは未取得です。以下はコードで確認した旧形式であり、Drive上の実在形式を保証しません。
旧APIは `diary_YYYY-MM-DD.json` に `{date,message,request_id?}` を保存し、
recipient / tags / sourceを保持していませんでした。旧CLIは日記解析結果の配列またはCSVです。
失われた宛先等を本文から推測して復元しません。既存ファイル・旧イベントの自動改名、削除、取り込みは行いません。

1. 旧フォルダとCalendarを読み取りで棚卸しする。Drive file ID、版、名前、内容ハッシュとCalendar event IDを控え、原本をバックアップする。
2. 日記データはそのまま日記として保管する。配信用データだけについて、欠落した宛先・タグ・入力元を所有者が確認する。
3. 新しい検証台帳と別のDriveフォルダ/テストCalendarを用意する。旧実イベントと新しい固定IDの対応は自動認識されない。
4. 移行用request_idを `legacy:<file-id>:<revision>` のように固定し、補った内容と元データの対応表を保存する。
   `source=legacy-import`、`memory_refs=["drive:<file-id>"]` 等を含む入力JSONを作る。
5. `grave-deliver --enqueue migration.json --dry-run` で入力検証し、`--enqueue` で外部送信せず登録する。
   欠落情報が解決していないもの、既に旧Calendarへ配信済みのものは保留リストに残す。
6. 件数・本文・宛先・日付・出典を照合後、新方式で配信を再開する範囲を承認する。
   配信済み旧イベントを移行しただけで新方式のジョブへ流すと二重掲載になるため、そのまま流さない。

ロールバックは新API / ジョブを停止し、旧原本とバックアップへ戻します。移行で原本を消さないため、
新しい台帳を隔離して再検証できます。旧イベントとの自動紐付けは実装していません。

### API互換性の変更

POSTのURLと既存の入力項目は維持しますが、応答は0.2.0で変更しています。
`storage_type:document` と「DriveまたはCalendar IDとしてのrecord_id」は廃止し、
`storage_type:record` と永続台帳IDへ変更しました。Google IDはそれぞれの専用フィールドです。
利用クライアントとGPTs Actionsのスキーマを同時に更新し、古いrecord_idを新しいGETへ渡さないでください。
入力不正は422、認証不正401、競合409、存在しないID404、内部/設定不良500で `error,message` を返します。
API_KEYを共有する利用者は同じ台帳にアクセスする設計で、個別ユーザー認証・宛先別権限は未実装です。
